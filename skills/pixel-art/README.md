# 像素画板（pixel-art）

画 16~64 像素的像素画，画完**整数倍等比放大**（最近邻，不做插值，所以不会糊）后直接发到当前会话。
输出**一律是不透明底**（透明底已禁用），不会出现透明像素。

## 装在哪

```
D:\qq agent\resources\app\skills\pixel-art\
├── skill.json     清单（技能页读它）
├── index.js       入口：两个工具 + 手写 PNG 编码器 + 四种生成器
└── README.md      本文件（程序不读，删掉不影响运行）
```

> 「技能」页签里应该能看到 **像素画板**，状态「生效中」，带 2 个工具：
> `pixel-art__draw_pixel_art`、`pixel-art__random_pixel_art`。
> （技能目录在**安装目录的 resources\app\ 下**，这是加载器写死的：它以自己的文件位置
> 为锚点找 `skills/`，不是以 exe 所在目录为锚点。）

## 机器人怎么用它

| 工具 | 什么时候用 | 关键参数 |
|---|---|---|
| `draw_pixel_art` | 群友说「画个像素爱心」「画个像素笑脸/星星/小房子」 | `art` 字符网格、`palette` 配色、`size` 尺寸 |
| `random_pixel_art` | 「随机来张像素画」「随便画个像素头像」，或说不出画什么 | `style` 风格、`size`、`seed` 种子 |

图片由工具**直接发出去**，机器人只需要配一句短话。

## 颜色字符表（`art` 参数用）

`art` 是一个字符串数组，**每个字符串是一行**（从上到下），**每个字符是一格**：

| 字符 | 含义 | 字符 | 含义 |
|---|---|---|---|
| `.` | 背景（不透明底） | `b` | 蓝 |
| `0` `1` `2` | 这套配色里的最暗 / 中间 / 最亮 | `p` | 紫 |
| `k` / `w` | 黑 / 白 | `m` | 粉 |
| `r` / `o` / `y` | 红 / 橙 / 黄 | `e` / `s` | 肤色 / 灰 |
| `g` / `c` | 绿 / 青 | | |

字符是**语义化**的：写 `r` 永远是「这套配色里的红」，不用去记第几号色。
16 行的红色爱心长这样：

```json
["................","................","...rrr....rrr...","..rrrrr..rrrrr..",
 ".rrrrrrrrrrrrrr.",".rrrrrrrrrrrrrr.",".rrrrrrrrrrrrrr.","..rrrrrrrrrrrr..",
 "..rrrrrrrrrrrr..","...rrrrrrrrrr...","....rrrrrrrr....",".....rrrrrr.....",
 "......rrrr......",".......rr.......","................","................"]
```

硬约束：最少 16 行、最多 64 行，每行的字符数要相同、且也在 16~64 之间。
写错了不会静默失败——工具会把「第几行第几个字符不认识」一次性列出来（最多 6 处）回给模型让它自己改。

## 各行字符数不一致会自动对齐（不再是失败）

排像素时最容易翻车的不是颜色，而是**各行字符数不相等**：想画 16×16，结果中间几行写成 17 个、
有一行又写成 15 个。真实发生过——同一个模型连试两次都栽在这上面（第一次第 5 行 17 个、
第二次第 10 行 15 个），用户看到的只是「失败了」，而且报错一次只说一行，改完这行又错另一行。

现在这类问题**不再失败**，改成自动对齐：

1. 目标宽度 = **出现次数最多的行宽**（并列时取第一行的宽度，也就是模型声明的意图）
2. 偏短的行 → 右侧补 `.`（背景色）
3. 偏长的行 → 从「填充字符更多」的那一侧裁掉，尽量让图案保持居中
4. 改了什么会**明确写进返回给机器人的文本**并打进日志，例如：
   `⚠️ 各行字符数不一致，已自动按多数行的宽度 17 对齐（第 1~4 行 16→17 个字符，第 15~16 行 18→17 个字符）`

这样模型既拿到了图，也知道自己这轮写错了，还会被提示「下次逐行数一遍」。
只有真正修不了的才报错（行数不在 16~64、宽度不在 16~64、有非法字符、全是 `.`）。

## 背景（透明底已禁用）

所有输出都是**不透明**的，一个透明像素都没有。`art` 里写 `.` 等于「这一格用背景色」。

底色由「背景」设置决定：

| 值 | 效果 |
|---|---|
| `auto`（默认） | 每套配色有自己的首选底色：糖果/红白机/柔和/高饱和用**浅底**，暗夜霓虹用**暗底**，四色绿用经典 Game Boy 的**亮绿屏**。只有当画面本身和这个底色太接近（例如在糖果配色上画一个纯白方块，会「白画白底」看不见）时，才自动翻到另一档 |
| `white` | 一律纯白底 `#ffffff` |
| `black` | 一律纯黑底 `#000000` |

auto 实际选了哪个色，工具会在返回给机器人的文本里写明（例如「背景是不透明的 #ece7f5」），
所以机器人答得上「这是白底还是透明底」。

## 尺寸与放大

- **逻辑像素**：16~64（模型自己选，默认 32）。
- **放大倍数是整数**，由「放大后的目标边长」（默认 384）自动算：
  16 像素 → ×24、32 像素 → ×12、64 像素 → ×6，最终都是 384×384。
- 因此永远不会出现 384/16 = 24.0 之外的插值糊边。

## 四种随机风格

`sprite` 左右对称的小生物（带描边、明暗、眼睛）· `pattern` 万花筒花纹（中心有徽记）·
`badge` 宝石徽章 · `landscape` 风景（天空渐变 + 日月 + 山脊）。`random` 随机挑一种。

同一颗 `seed` 永远画出同一张图；工具的返回文本里会带上种子，群友想「再来一张一样的」就把它填回去。

## 设置页能调什么

| 设置 | 默认 | 说明 |
|---|---|---|
| 默认画布边长 | 32 | 模型没指定尺寸时用它 |
| 放大后的目标边长 | 384 | 发出去多大 |
| 单格最大放大倍数 | 32 | 防止意外生成超大图 |
| 默认配色方案 | auto | 手绘时用糖果配色（保证红爱心真是红的），随机生成时每次换一套 |
| 背景（透明底已禁用） | auto | auto / white / black，见上面「背景」一节 |
| 额外发一条尺寸说明 | 关 | 开启后工具会补一条「32×32 · 糖果配色 · 放大 12 倍 · 背景 #ece7f5」 |
| 本地留档张数 | 30 | 画好的 PNG 只留最近这么多张 |

## 图片存哪

`<数据目录>\pixel-art\`，即 `D:\qq agent\data\pixel-art\`。
发送失败时这张图还在本地，返回文本里会给出完整路径。

## 实现说明（为什么零依赖）

这个装好的 App 的 `node_modules` 里**没有** canvas / sharp / jimp / pngjs / pureimage
任何一个图形库。为了不引入需要联网安装、还要重启的依赖，`index.js` 用 `node:zlib`
的 `deflateSync` + 自算 CRC32 手写了一个最小 PNG 编码器（RGBA、8 位、无隔行，
逐行在 None/Sub/Up 三种滤波器里挑最省字节的）。RGBA 的 alpha 恒为 255——
透明像素在**放大之前**就已经被 `flattenBackground()` 落成背景色了，
所以放大的是"合层"后的结果。

其余约定：发图一律走 `ctx.sender.sendImage`（队列/限频/去重/留档都在里面，不绕过它直连
OneBot）；配置在执行时用 `cfg()` 现读；参数先校验、失败返回 `isError` 而不是抛错；
图片只发一次（既 `sendImage` 又返回 `image_url` parts 会发两张，所以只走前者）。
